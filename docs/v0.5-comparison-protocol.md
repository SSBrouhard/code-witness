This protocol reuses the v0.4 protocol

## Question

What does Code Witness contribute beyond a capable coding agent?

v0.4 showed that Codex with Code Witness, working blind, built a baseline that
beat one project's own test suite. It did not show that Codex needed Code
Witness to do it. v0.5 runs the same agent on the same target under two
conditions that differ only in whether Code Witness is available, and evaluates
both identically.

| Condition | Agent | What it delivers |
| --- | --- | --- |
| **A** | Codex with Code Witness | A Code Witness contract pack, with its adapter and fixtures |
| **B** | Codex alone | A pytest characterization suite, with any recorded data it needs |

The result is one of three decisions, computed mechanically (section 4):
- **GO**: Code Witness added measurable value on this target. Keep investing in it as built.
- **PIVOT**: Code Witness did not add measurable value over Codex alone, or Codex alone did better. Reconsider its role before expanding it.
- **INCONCLUSIVE**: the run was invalid, the conditions split, or run-to-run variation was too large to call.

A PIVOT is an acceptable and useful answer. The design must not favor either condition.

## What this experiment is not

- Not a modernization test. A real migration is deferred to v0.6.
- Not a statistical proof. Two runs per condition on one target is a screening decision about whether to keep investing, not a significance test (section 4.5).
- Not a benchmark of models. Both conditions use the same model, effort and settings.

## Fixed constraints

1. One target, selected by rule (section 6), not used in any earlier Code Witness work and without a readily available public behavioral specification.
2. Four investigator runs: two per condition (A1, A2, B1, B2). Each is a fresh, isolated session with its own runtime home and workspace. No run can read another run's workspace, home or output.
3. The two conditions differ only in the Code Witness wheel, its README, the brief's condition-marked lines (tool description, detection rule and deliverables), and the deliverable format. Everything else is identical: model, reasoning effort, runtime version, flags, sandbox profile, Python, installed test tools, guide, time budget and evaluation (section 2).
4. One evaluation set (mutants and challenges) is created after all four baselines are frozen. It is generated independently of both conditions and used unchanged for all four runs and the upstream suite.
5. Criteria, thresholds, the decision rule, budgets, stop conditions, seeds and timeouts are fixed by this document and the preregistration before the first investigator starts. Nothing is tuned after any baseline is frozen.
6. Upstream tests, their history and any upstream test data are hidden from every investigator and the challenger.
7. Roles run on the owner's existing subscription-authenticated Codex CLI, with no API keys, usage billing, paid credits or custom orchestrator. No operating-system accounts or cloud infrastructure.
8. No Code Witness engine changes from protocol approval until the report is written. Supporting experiment tooling under `experiments/` may be added before preflight only (see "Tooling required before preflight").
9. Withheld evaluation material is never committed to this public repository. The target is not named in this repository before the report.

## Conditions and fairness

### What both conditions get

Every investigator workspace contains, byte for byte the same across all four runs except where noted:
- `repo/`: a fresh clone of the stripped target (tests and test history removed), with an identical tree hash in every workspace.
- `.venv/`: CPython 3.13 with `pytest==9.1.1` and `coverage==7.17.0`. Condition A additionally has the pinned Code Witness wheel and its two dependencies (`tree-sitter`, `tree-sitter-python`). Preflight P8 checks that `pip freeze` differs only by those packages.
- `CHARACTERIZATION-GUIDE.md` (Appendix B): neutral advice on characterization testing that applies to both conditions.
- `BRIEF.md` (Appendix A): the same text for both conditions except the lines marked for one condition: the tool description, the detection rule and the deliverables.
- `tmp/`.

Condition A also gets `CODE-WITNESS-README.md`. Condition B's workspace contains no mention of Code Witness.

### What makes Codex alone a fair competitor

Condition B is designed to have a genuine chance at an excellent result:
- **Same information about evaluation.** Both briefs explain how detection is judged, that false alarms count against the baseline, and that the baseline must replay deterministically from a fresh environment. B is told exactly which pytest outcomes count as detections, because pytest has failure modes (collection and setup errors) that Code Witness does not.
- **Same tools.** B has pytest and coverage, the same as A. B may write helper scripts, generate recorded expected outputs by running the current code (golden-master style), parametrize heavily, and store data files. It can do everything Code Witness does conceptually, by hand.
- **Same guide.** Both conditions get Appendix B, so A does not get better testing advice through its README.
- **Same time.** Four hours each, one session, with "use the time you need" in both briefs.
- **A fixed run command.** B is told the exact command the evaluator uses, and A the exact extract command, so neither loses detections to an unexpected invocation.
- **Isolation from upstream configuration.** B's suite runs with its own config file (`-c _characterization/pytest.ini`), its own root and `--confcutdir`. The target's own `conftest.py`, `pytest.ini` or `pyproject` settings come back in the scoring tree, and none of them can change B's results.
  - A check during drafting showed that `--rootdir` and `--confcutdir` alone still let a repository-root `pytest.ini` apply its `addopts`. `-c` stops this.
  - Setup pre-creates `_characterization/pytest.ini` containing only `[pytest]`, so B's suite never fails for lack of it.
  - P7 proves the isolation.
- **Neutral wording.** Neither brief praises Code Witness or describes it as the preferred approach. The owner's review of Appendix A and Appendix B in this PR is the neutrality check.

### Known asymmetries that remain

These are inherent to the two formats. They are reported, and none is resolved in either condition's favor:
- Code Witness runs every fixture in a fresh process with a fixed 5 s case timeout. A pytest suite runs in one process with a suite-level timeout (section 1.3). Timeouts are never detections in either condition.
- Code Witness treats any observation difference as a detection. pytest counts only assertion failures and exceptions raised from target code; collection, setup and import errors are errors, and other failures go to adjudication. These are the v0.4 rules for the upstream suite, applied unchanged to condition B.
- Code Witness fingerprints source files. A pytest suite does not. Fingerprints are not part of any measure.

## Roles and boundaries

| Role | Sessions | Sees | Never sees |
| --- | --- | --- | --- |
| Coordinator | One agent session acting for the owner | Everything | Never edits a role's artifacts after hand-in |
| Investigator | Four fresh sessions, one per run, each with its own `CODEX_HOME` | Its own workspace only | The protocol, the preregistration, the other condition, the other runs, upstream tests, mutants, challenges, scoring rules beyond the brief, any session history, the owner's instruction files, the network |
| Challenger | One fresh session (plus one replacement round if needed) | Its own copy of the stripped repo | Any baseline, upstream tests, mutants, scoring rules, other workspaces |
| Adjudicator | Fresh sessions, packets only | Only the packet for each judgment | Which suite killed what, the condition behind a run label, unless the packet's own content reveals the format |
| Scorer | `score.py` and `compare.py`, run by the coordinator in the scoring sandbox | Frozen baselines, pristine repo, mutants, challenges | n/a (no judgment) |
| Owner | Stephen | The final report and the approvals in this document | Is never asked to design tests, choose scenarios, pick the target or explain code |

**Neutral run labels.** Runs are labeled W, X, Y and Z. The mapping from labels
to A1, A2, B1 and B2, and the run order, come from the preregistered seed. The
mapping is sealed, and adjudicator packets use labels only. Deliverable formats
reveal the condition to anyone who reads them, which is recorded as a limit.

**Isolation.** Unchanged from v0.4 "Isolation design", as amended:
- the same deny-root permission profile and `codex exec` flags
- `env -i` launch, `RUST_LOG=codex_core=debug` for model evidence (A1)
- Codex CLI at the version verified in P1 (A2)
- one dedicated, owner-signed-in `CODEX_HOME` per role session

There are six homes: four investigators, one challenger, one adjudicator. A
replacement challenger round reuses the challenger home after its session state
is deleted. Each investigator home is used by exactly one run, so no session
state, cache or log can carry knowledge between runs.

## 1. Evaluation set (frozen and shared)

### 1.1 Mutants

v0.4 section 2 applies, with these changes:
- **Five suites per mutant.** Each suite has its own copy of the scoring tree, with identical source and its deliverable at its original path.
  - Two runs of a condition use the same deliverable directory name, so they cannot share one tree. Separate trees also stop one run's files from affecting another's.
  - Each valid mutant is applied to all five copies.
  - A suite's result counts only if its tree's diff hash equals the mutant's hash, checked before restoration.
- **Sample.** At most 400 mutants, drawn with the preregistered seed, the same for every suite.
- **Primary denominator D** = valid mutants killed by at least one of the five suites, plus adjudicated `not-equivalent` mutants. All five suites are scored on the same D.
  - Only suites that passed clean replay (G1) contribute kills to D.
  - A suite that fails on unchanged code would report every mutant as killed, so its results cannot define D.
- **Kill rate** K(suite) = that suite's kills within D divided by D.
- **Witness suites** (condition A) use the v0.4 witness rule: a kill is at least one fixture whose observation differs from the frozen pack.
- **pytest suites** (condition B and upstream) use the v0.4 junit classification: `assertion` and `target-exception` are kills; `dependency`, `collection` and `setup` are errors; anything else is `adjudicate`.
- **Equivalence.** A mutant survived by all five suites gets an equivalence verdict. A `not-equivalent` verdict needs a distinguishing input that the coordinator executes on the pristine and mutated trees (v0.4 runner, with `TMPDIR` inside the adjudicator workspace).

### 1.2 Challenges

v0.4 section 3 applies, with these changes:
- **Counts.** The challenger writes 24 regressions (`R01` to `R24`) and 24 behavior-preserving controls (`N01` to `N24`).
  - The first 20 valid regressions in ID order are scored.
  - All valid controls are scored, and at least 16 are required.
  - A shortfall triggers one replacement round, as in v0.4.
- **Timing.** The challenger starts only after all four baselines are frozen. It never sees any baseline.
- **Reclassifying a control.** A valid control that any suite flags is reclassified as `behavior-changed` only when the adjudicator supplies a distinguishing input and the coordinator's execution confirms different results on the pristine and patched trees. A reclassified control is removed from the control set for **every** run and the upstream suite, so all runs keep the same denominator. Otherwise the flag is a false alarm for that run. An `indeterminate` verdict also counts as a false alarm.
- **Untested controls.** A valid control on which a run did not reach an outcome (`timeout`, `error`, or an unresolved `adjudicate`) makes that run's false-alarm count not evaluable.
- **Detection.** A regression is detected by a run when that run's suite reports `behavioral` on it. A timeout or error counts as not detected.

### 1.3 Timeouts

- **Witness suites.** The engine's fixed 5 s case limit.
- **pytest suites.** The larger of 60 s and 10 times that suite's own median clean run, measured on three clean runs before any mutant runs. The upstream timeout is fixed in preflight; each condition-B timeout is fixed from that run's clean replay, before mutants. Every timeout is recorded in `comparison.json`.

## 2. Per-run measures (identical for both conditions)

Every measure is computed by the scorer for each run W, X, Y and Z, and for the upstream suite where it applies.

| ID | Measure | Condition A (pack) | Condition B (pytest suite) |
| --- | --- | --- | --- |
| K | Kill rate on D (section 1.1) | Witness rule | junit rule |
| R | Held-out regressions detected, out of 20 | `behavioral` | `behavioral` |
| F | False alarms on valid controls (count) | Flagged, not reclassified | Same |
| G1 | Clean replay: 3 of 3 clean runs on the unmodified scoring tree | No mismatch, timeout or error | Exit 0, no failure or error |
| G2 | Knockout: share of units that change when every target-scope function body raises a dedicated knockout exception. Pass at 80% or more; `insufficient-evidence` when blocked or errored units could decide it (v0.4 rule). | Unit is one fixture | Unit is one collected test item; it changes when it fails with `assertion` or `target-exception` |
| G3 | Oracle review by the adjudicator: does the deliverable compute expected results itself instead of recording the real code's behavior? Verdict `none`, `reimplements`, `self-referential` (expected values produced by calling the code under test during the run) or `indeterminate`. Pass only on `none`. | Adapter and fixtures | Test code, helpers and data |
| G4 | Reproducibility: replay passes in a fresh environment, at a different absolute path, containing only a fresh stripped clone at the pinned SHA, a venv rebuilt from the same pinned packages, and the deliverable directory. It must pass under `PYTHONHASHSEED=0` and `PYTHONHASHSEED=1`. | The pack's own generated test and the scorer's witness replay | The fixed run command; also in reverse collection order |
| C | Claims accuracy: share of sampled `Verified` claims the adjudicator rules `supported`. Up to 10 per run, every k-th in file order. Not evaluable for a run with fewer than 5 `Verified` claims. | `CLAIMS.md` | `CLAIMS.md` |
| E | Preparation effort, reported only: investigator wall-clock, reported tokens, turns, shell commands run, time to first passing replay, deliverable size | From the event log | Same |
| V | Coverage of the target scope by line and branch, reported only | `fixture_coverage.py` | `coverage run -m pytest` with the fixed command |

A run **passes the reliability gates** when G1, G2, G3 and G4 all pass.

The upstream suite gets K, R, F, G1 and coverage as a reference. It is never
part of the GO / PIVOT / INCONCLUSIVE comparison, except as the floor in
section 4.3.

## 3. Validity

The experiment is **valid** only when every one of these holds. Otherwise the decision is INCONCLUSIVE.

| ID | Condition |
| --- | --- |
| V1 | `PREFLIGHT.json` passed, and every frozen baseline matches its hash in its `FREEZE.json` |
| V2 | No S3, S4 or S7 incident is recorded for any run, the challenger or scoring |
| V3 | All four investigator runs started and were frozen. A run that failed to start, or was invalidated, is replaced once, and only if this is found before the evaluation set exists (section 9.2). |
| V4 | Mutant results match the sampled mutant ids exactly once for every suite, every survivor of all five suites has an equivalence verdict, and the persistent-error share is at most 5% for every suite |
| V5 | D contains at least 100 mutants |

**A run without a usable baseline is still a valid run.** That covers a run
with no deliverable, and a run whose deliverable fails clean replay (G1),
including a deliverable that passes only 2 of 3 times. Such a run is scored as
follows, the same in both conditions:
- K = 0 and R = 0.
- F = the number of valid controls. A suite that fails on unchanged code flags everything.
- G1 to G4 fail.
- C is scored from its claims if it has any.

This stops a failing suite from looking like a perfect detector, and stops an
empty deliverable from scoring zero false alarms.

A metric that cannot be computed for one run (for example F with an untested
control, R with fewer than 20 valid regressions after the replacement round, or
C with too few claims) is **unresolved**. This does not invalidate the
experiment.

## 4. Decision rule

### 4.1 Thresholds (fixed before preregistration)

| Metric | Better when | Meaningful difference T |
| --- | --- | --- |
| K kill rate | higher | 5 percentage points |
| R regressions detected | higher | 3 regressions (15 percentage points of 20) |
| F false alarms | lower | 2 false alarms |
| C claims accuracy | higher | 25 percentage points |
| Reliability gates | more runs pass | see 4.2 |

For context, v0.4's baseline beat the upstream suite by 8.8 points on K and by
3 regressions on R. Run-to-run variance of one condition is unknown, which is why
it is measured here rather than assumed.

### 4.2 Comparing the conditions on one metric

For K, R, F and C, orient each value so that higher is better (use minus F).
With A-run values a1, a2 and B-run values b1, b2:
- **d** = mean(a1, a2) minus mean(b1, b2): the difference between conditions
- **s** = the larger of |a1 - a2| and |b1 - b2|: the run-to-run spread within a condition
- **gA** = min(a1, a2) minus max(b1, b2): above zero means every A run beat every B run
- **gB** = min(b1, b2) minus max(a1, a2): the same for B

| Result | When |
| --- | --- |
| **A advantage** | d is at least T, gA is above 0, and d is greater than s |
| **B advantage** | minus d is at least T, gB is above 0, and minus d is greater than s |
| **Tie** | the absolute value of d is below T, and s is at most T |
| **Unresolved** | anything else, including a metric that is not evaluable for any run |

So a difference counts only when it is meaningful (at least T), consistent
(every run of one condition beats every run of the other), and larger than the
noise between runs of the same condition. A marginal or noisy difference is
never forced into a winner.

**Reliability gates.** With pA and pB the number of runs in each condition that pass all of G1 to G4:
- **A advantage**: pA = 2 and pB = 0.
- **B advantage**: pB = 2 and pA = 0.
- **Tie**: pA = pB.
- **Unresolved**: 2 against 1, or 1 against 0. One failing run is not enough to call a condition less reliable.

### 4.3 Absolute floor for GO

Beating a weak Codex-alone result is not enough. GO also requires **both A runs** to meet this floor:
- K at least the upstream suite's K minus 10 points (the v0.4 C3 margin)
- R at least 14 of 20
- F at most 2
- all reliability gates pass

### 4.4 Outcome

Computed by `compare.py` from `comparison.json` inputs, in this order:

1. **INCONCLUSIVE (invalid)** if any of V1 to V5 fails.
2. **GO** if A has an advantage on at least one of K, R, F or the reliability gates; B has no advantage on K, R, F, the reliability gates or C; and both A runs meet the floor in 4.3.
3. **PIVOT** if either:
   - B has an advantage on at least one of K, R, F or the reliability gates, and A has no advantage on any of K, R, F, the reliability gates or C; or
   - K, R, F and the reliability gates are all ties, **and** C is a tie or a B advantage.
4. **INCONCLUSIVE** otherwise. This covers:
   - mixed advantages
   - differences that are not separated from run-to-run noise
   - an A advantage whose runs miss the floor
   - an A advantage on claims accuracy alone
   - ties on K, R, F and the reliability gates when C is unresolved

**Claims accuracy (C) is never a primary trigger, and its result is read literally:**

| C result | Effect on GO | Effect on PIVOT |
| --- | --- | --- |
| A advantage | Allowed | Blocks both PIVOT branches |
| B advantage | Blocks GO | Allowed in both branches |
| Tie | Allowed | Allowed in both branches |
| Unresolved | Allowed: GO already rests on a primary A advantage | Allowed in the first branch, which rests on a primary B advantage. **Blocks the second branch**: "no measurable value" needs evidence of a tie, and an unresolved C is not evidence of one. The outcome is then INCONCLUSIVE. |

Unresolved never counts as a tie for any metric. `compare.py` represents the
five results as `A`, `B`, `tie` and `unresolved`, and tests every cell of this
table and every branch.

The report states which branch fired and lists every metric's result, so the
reasoning can be checked by hand.

**Examples** (illustrative, not predictions):

| A runs K | B runs K | Other metrics | Decision |
| --- | --- | --- | --- |
| 93, 91 | 84, 82 | all ties; A meets the floor | GO: A advantage on K (d = 9, gA = 7, s = 2) |
| 93, 80 | 84, 82 | all ties | INCONCLUSIVE: K is unresolved (d = 3.5 is below T, and s = 13 exceeds T) |
| 90, 89 | 88, 90 | all ties | PIVOT: K is a tie (d = 0.5, s = 2), so no measurable value |
| 90, 89 | 88, 90 | R, F and gates tie; C unresolved (a run has fewer than 5 Verified claims) | INCONCLUSIVE: the second PIVOT branch needs C to be a tie or a B advantage |
| 88, 87 | 94, 93 | all ties | PIVOT: B advantage on K (d = -6, gB = 5, s = 1) |
| 93, 92 | 85, 84 | F: A runs 5 and 5, B runs 1 and 1 | INCONCLUSIVE: A advantage on K, B advantage on F |

### 4.5 What the decision can and cannot carry

With two runs per condition, if the two conditions were truly identical, every A
run would beat every B run on a given metric about 1 time in 6 by chance alone.
The threshold T and the spread test reduce that, but do not remove it. A GO
means "measurable value on this target, worth further investment and
replication". It does not mean "proven in general". A PIVOT means "no
measurable advantage for Code Witness as built, on this target". It is a reason
to reconsider Code Witness's role, not proof that it can never add value.
Three runs per condition would cut the chance-ordering figure to 1 in 20 at
50% more investigator cost. See "Decisions".

## 5. Budgets, interventions, time accounting and stop conditions

Budgets are ceilings, not targets.

| Budget | Ceiling |
| --- | --- |
| Investigator, per run | 4 hours wall-clock, one session, at most 2 restarts after runtime crashes. The same for all four runs. |
| Challenger | 2 hours, including a replacement round |
| Aggregate agent-hours | 34, counted as in "Time accounting" |
| Reported tokens | 80 million in total. No per-run token cap: investigation quality is not limited to save tokens, and the time cap binds first. |
| Incremental paid usage | USD 100, and only with explicit owner authorization recorded in advance. Expected: USD 0. |
| Calendar | 4 days from preregistration to the last agent session |
| Owner attention | At most 10 interventions and 60 minutes in total. Six sign-ins are planned. Zero interventions in the test-design or code-explanation categories. |
| Scorer compute (not agent time) | 16 hours across clean replay, mutants, challenges, knockout, reproducibility and coverage. Parallel shards on separate tree copies are allowed, with an identical procedure per mutant. |

**Planning allocation** within the 34 agent-hours:
- investigators 16 (4 x 4)
- challenger 2
- adjudicator 5
- coordinator 9
- P1 probe sessions 2

Only the per-investigator cap and the aggregate are binding.

**Time accounting** (preregistered, from the v0.4 lesson):
- **What counts.** Every role session's full wall-clock, plus the coordinator's active time. Active time includes reasoning, tool execution, retries, and waiting on a running background job or role session.
- **What is excluded.** Only a coordinator period that is waiting for an owner message, and only when the logs show all of the following for that period:
  - no coordinator event
  - no running background job
  - no running role session
  - no write under the experiment root

  The check is the one used for v0.4 `TIME-VERIFICATION.json`.
- **Overlap.** Role sessions are counted in full even while the coordinator waits on them. That overlap is counted twice, deliberately.
- **Elapsed time.** Total elapsed wall-clock is always reported beside the agent-hours.

**Rate limits.** If the subscription rate-limits a role session:
- Time the runtime spends waiting on a rate limit is taken from its debug log and recorded per session.
- That waiting time does not count against an investigator's 4-hour cap, so a rate limit cannot shorten one run's working time more than another's. It does count toward aggregate agent-hours.
- A rate limit that ends the session counts as a restart.
- Two failures of the same kind trigger S5.

**Logs.** Usage, intervention and incident logs follow v0.4 section 4, with one `USAGE.jsonl` row per session and the run label on investigator rows.

**Stop conditions.** v0.4 S1 to S7 apply, with these changes:
- **S1, investigator.** The run's budget ends: freeze what exists and score it. A run with no deliverable is scored as a run without a usable baseline (section 3).
- **S8, condition imbalance.** Before the evaluation set exists, if a run fails to start twice or is invalidated by S3 or S4, one replacement run is allowed for that run label, with a new home and workspace. After the evaluation set exists, no replacement is possible; V3 fails, and the decision is INCONCLUSIVE.
- **Order.** The challenger, mutant enumeration and scoring never start until all four runs are frozen.

## 6. Target selection (coordinator)

Required properties:
- **Repository.** Public, under an MIT, BSD or Apache-2.0 license, not owned by Stephen.
- **Not used before.** Not chevron, dpath-python, or any repository considered in v0.4's `SELECTION.json`.
- **Fewer than 300 GitHub stars** (v0.4 used fewer than 1,000), to lower the chance the models know it. The star count is recorded.
- **No readily available public behavioral specification.** The target scope must not implement a named external format, protocol, standard or language that has a published specification, conformance suite or test vectors. Examples: an RFC, ISO or W3C format; Mustache; cron; semver; JSON, YAML, TOML or INI; Markdown; a CSV dialect; a regular-expression flavor; a date format standard.
  - The repository's README and docs must not link to such a specification as the behavior they implement.
  - The project's own prose documentation is allowed: a maintainer would have it.
  - Record the evidence for each candidate: README and doc links, and any specification found by a web search for the project name together with "spec", "specification", "conformance" and "test vectors".
- **Pure Python.** Runtime dependencies from the standard library only, vendored modules counting as in-repo. Supports CPython 3.13.
- **Harder than v0.4.** Code lines are counted with the A3 method, which excludes blank lines, comments and docstrings.
  - The target module has 250 to 900 code lines and imports at least 2 in-repo modules.
  - The target scope (the module plus the in-repo modules it imports by name) has 500 to 1,500 code lines.
  - At least one of these holds:
    - a public class whose instance state persists across method calls and changes their results
    - at least 80 branch points in the scope by a preregistered AST count: `if`, `elif`, `for`, `while`, each `except` handler, each `match` case, each conditional expression, each comprehension condition, and each extra operand of `and` and `or`
- **Deterministic scope.** No network, subprocesses, threads, async, randomness or wall-clock time in the scope, or those effects can be avoided through the public API. Use the v0.4 grep and read every hit. File I/O is allowed only to paths the caller supplies.
- **Upstream suite.**
  - pytest can run it, and it exercises the target module.
  - It passes at the pinned SHA and finishes in under 2 minutes.
  - It passes 10 consecutive sandboxed runs on one tree with all test state kept between runs (A8).
  - Its line coverage of the target scope is between 60% and 95%.

Procedure:
1. Examine up to 8 candidates and record every one in `sealed/SELECTION.json` with each property's evidence and the reason for any disqualification.
2. Pick the qualifying candidate whose upstream scope line coverage is closest to 80%. Tie-break: the larger branch-point count.
3. Do not consult the owner. The target is not named in this repository before the report.
4. **If none of the (at most 8) candidates qualifies, stop.**
   - Record every candidate and its disqualification in `SELECTION.json`.
   - Report a selection failure to the owner, with the closest misses and which requirement each failed.

## Known limits of this design

- One target. Two runs per condition is a screening design (section 4.5).
- Both conditions use the same model family as the challenger and adjudicator. A shared blind spot would affect both conditions alike, so it biases the absolute scores more than the comparison.
- The deliverable format reveals the condition to the adjudicator for the oracle review, claims and control disputes. Execution-backed rules (control reclassification needs a confirmed input; not-equivalent needs a confirmed input) limit how much judgment matters there.
- Condition B's suite timeout and Code Witness's per-case timeout differ by design. Timeouts are never detections.
- Memorization risk is lowered, by the star cap and by the no-public-specification rule, but not removed.
- The coordinator is a Claude session that has worked on Code Witness. Every measure and the decision are computed by committed scripts from preserved evidence. Recording incidents honestly still depends on the coordinator, as in v0.4.

## Decisions

Approved by the owner on October 23, 2026, before drafting:
- two runs per condition, four in total, with identical model, effort, constraints and budgets
- numerical criteria and a decision rule with a meaningful-improvement threshold, a run-to-run variance check and an INCONCLUSIVE outcome
- identical evaluation for both conditions: mutation detection, held-out regressions, false alarms, clean replay, knockout, claims accuracy, preparation effort and reproducibility
- modernization deferred to v0.6
- one harder, unfamiliar target without a public behavioral specification; hidden upstream tests; isolated investigators; independent challenges; one frozen evaluation set

Proposed in this draft. In the PR #4 review the owner approved the thresholds, the GO floor, two runs per condition, the budgets, the six sign-ins, and the neutrality of Appendix A and Appendix B. The same review added two rules: an unresolved C never counts as a tie or triggers PIVOT (section 4.4), and selection stops if no candidate qualifies (section 6). Merging records final acceptance.

## Appendix B: characterization testing guide (both conditions)

Copied verbatim into every investigator workspace as `CHARACTERIZATION-GUIDE.md`.

```text
Characterization testing: notes

A characterization baseline records what code does today, so a later change
that alters that behavior is noticed. It pins current behavior, including
behavior that looks like a bug. It does not describe intended behavior.

Finding behavior worth pinning
- Start from the public API and from how the rest of the repository calls it.
- For each entry point, cover typical inputs, boundaries, empty and minimal
  inputs, unusual types, invalid inputs and every error path.
- Read the branches. Each condition, loop and exception handler is a place
  where a change can alter behavior. Use coverage to find lines and branches no
  scenario reaches: python -m coverage run --branch ..., then
  python -m coverage report -m.
- For stateful objects, record sequences of calls and what is observable after
  each step, not only single calls.

Recording results
- Record exact observable results: return values with their types, ordering,
  exact numbers, and exceptions with their type and message.
- Get expected values by running the current code and storing the results as
  literal data. Do not compute expected values with your own reimplementation,
  and do not call the code under test to produce the expectation during the
  check itself; then a changed result would change the expectation too.
- Review recorded results. A recording that captured an error from your own
  setup is not evidence about the code.

Keeping it reliable
- The baseline must give the same result every time: avoid dependence on wall
  clock, randomness, environment variables, hash seeds, set or dict ordering
  where the code does not guarantee it, absolute paths, test order and the
  network. Write any files only inside the directory you were given.
- Do not pin incidental details that a behavior-preserving refactor may change,
  such as object identities, memory addresses in reprs or private attributes.
  Do pin every observable output.
- Keep each scenario small and named so a failure points to one behavior.

Recording evidence
- Say what is covered and what is not. Mark a claim Verified only when a
  recorded scenario or an executed check directly shows it.
```
