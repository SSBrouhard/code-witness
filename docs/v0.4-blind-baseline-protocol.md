Supporting materials in [`experiments/v0.4-blind-baseline/`](../experiments/v0.4-blind-baseline/)
are none of them part of the `debt-compiler` engine:
- `score.py`: the deterministic scorer
- `assess.py`: the deterministic assessment and usage extraction
- `probe.py`: the isolation probe

- `preflight_canary.sh` and `canary/`: a committed canary used only for preflight
- `tests/`: regression tests for the scorer and the assessment

## Question

Can an independent coding agent, given only an unfamiliar repository and an
objective, use Code Witness to build a behavioral baseline that detects changes
it was never told about, and how does that baseline compare with the
repository's own test suite on the same changes?

This is one experiment on one target. It is not a framework, a benchmark suite
or a product release. Its result decides what, if anything, the engine needs next.

## Fixed constraints

1. One independent target.
2. Investigator, challenger, adjudicator and scorer are separate roles with enforced information boundaries.
3. Acceptance criteria, denominators, budgets and stop conditions are fixed by this document and the preregistration before the investigator starts.
4. The baseline is frozen and hashed before any challenge or mutant list exists.
5. The baseline and the upstream suite are scored against byte-identical mutations of the actual target implementation, under the same denominator rules.
6. Code Witness verification outcomes (PASS / FAIL / BLOCKED / INCONCLUSIVE), coverage, mutation detection, held-out regressions, false alarms, missing evidence, human intervention and cost are reported as separate measures. None of them changes another, and there is no combined score.
7. A failed safety or integrity preflight blocks the experiment until resolved. Isolation is never weakened to make the experiment run.
8. Nothing is tuned after freeze: fixtures, adapter, criteria, thresholds, denominators, scripts, seeds, timeouts and the challenge set stay as preregistered.
9. Roles run on the owner's existing subscription-authenticated agent runtimes (Codex CLI with ChatGPT sign-in, Claude Code with Claude subscription sign-in). No API keys, no usage-based billing, no paid credits and no custom agent orchestrator.
10. No Code Witness engine changes, security remediation, production actions, publication or pushes during the experiment. Withheld evaluation material is never committed to this public repository. No operating-system accounts or cloud infrastructure are created without separate owner authorization.

Anyone who follows this protocol must not need the owner to design tests, choose
mutations, pick the target or explain code. The owner's planned actions are:
- approving this document, which accepts the "Decisions" section
- signing in to role runtime homes where a runtime requires it
- reading the final report

Each of these is logged as an intervention (section 4).

## Roles and boundaries

| Role | Who | Sees | Never sees |
| --- | --- | --- | --- |
| Coordinator | One agent session (Codex or Claude Code) acting for the owner. Runs setup, preflight, the scorer, the assessment and the report. | Everything | Does not edit role artifacts after they are handed in |
| Investigator | Fresh session with no prior context, started from the brief in section 9.1 only | Its workspace: the target repo with tests and test history removed, the pinned Code Witness wheel and its README | This protocol, the preregistration, upstream tests, mutants, challenges, other role workspaces, any session history, the owner's instruction files, the network |
| Challenger | Fresh session. It may use the same model family as the investigator, as long as P1 shows the boundaries hold for its separate session. | Its own copy of the stripped repo | The baseline, upstream tests, mutants, scoring rules, other workspaces, any session history |
| Adjudicator | Fresh session with no prior context | Only the packet it is given for each judgment | Which suite killed what, and the investigator's artifacts unless a dispute requires them |
| Scorer | `score.py` and `assess.py`, run by the coordinator inside the scoring sandbox | Frozen baseline, pristine repo, mutants, challenges | n/a (no judgment) |
| Owner | Stephen | The final report, plus the approvals listed in this document | Is never asked to design tests, choose scenarios or explain code |

Boundaries are enforced in two ways, and preflight must demonstrate both (P1, P6).

**Ordering.**
- Upstream tests and their history are removed from the investigator's repo, and the coordinator's pristine clone is deleted before the investigator starts.
- Mutant lists, challenger patches and negative controls are created only after freeze.
- The only withheld material on disk while the investigator works is sealed coordinator files, and isolation must make them unreadable.

**Isolation.** See the next section.

## Isolation design

Four properties are required for every role session (investigator, challenger,
adjudicator) and for scoring:

1. **Model communication.** The agent runtime process keeps only the provider connectivity it needs for authenticated model requests, using the owner's existing subscription sign-in.
2. **Target execution.** Every command the agent runs (unfamiliar source code, tests, subprocesses, mutation tooling) executes with no outbound network access, including through any proxy the runtime injects. Reads and writes are limited to the role workspace plus the read-only runtimes it needs.
3. **Information boundaries.** No path a role can use (shell commands, native file tools, image or web tools, MCP servers, memories, plugins, injected instruction files) reaches another role's workspace, sealed material, any agent's session history, the owner's instruction files or unrelated user files.
4. **Credentials.** Provider authentication material (auth files, keychain items, tokens in environment variables) is not readable by target code, adapters, test processes or other roles. No authentication secret is copied into any workspace or source tree.

These properties are separate. The runtime process needs the network to reach its
provider, so isolation comes from the runtime's own supported command sandbox
and tool configuration, not from cutting the runtime off. A shell sandbox does
not automatically restrict a runtime's native tools, so P1 tests every execution
path separately.

### Launch rule

Every role session and every scoring command starts from a scrubbed environment
(`env -i` plus an explicit allow-list of variables). The investigation found
that a session started inside the Claude desktop app inherits the app's own
`ANTHROPIC_AUTH_TOKEN` and other credentials, and every child process sees them.

## 1. Acceptance criteria

`assess.py` computes every criterion mechanically from frozen inputs and recorded
results (section 9.6). Each is reported as met, not met or not evaluable, with
the numbers behind it. "Not evaluable" counts as not met.

| ID | Criterion | Threshold |
| --- | --- | --- |
| C1 | Valid run | `PREFLIGHT.json` passed; `baseline.tar` matches the SHA-256 in `FREEZE.json`; no S3, S4 or S7 incident recorded |
| C2 | Baseline integrity | The frozen pack's verification outcome is not BLOCKED; clean replay passes 3 of 3 for both suites; knockout status is `pass` (at least 80% of fixtures show an **observed changed observation**; section 9.4 step 6); the adjudicator's adapter review is `none` (no reimplementation of target logic) |
| C3 | Mutation detection versus upstream | On the primary denominator D (section 2), the baseline's kill rate is at least the upstream suite's rate minus 10 percentage points. "Exceeds upstream" is reported when it is higher. |
| C4 | Held-out regressions | Exactly 10 valid, independently developed regressions are scored, and the baseline detects at least 7 |
| C5 | False alarms | At least 10 valid behavior-preserving controls are scored, and the baseline flags at most 1 of them |
| C6 | Supervision | Zero interventions in the test-design or code-explanation categories; at most 8 interventions and at most 45 minutes of owner time in total |
| C7 | Cost | At most 12 agent-hours in aggregate; investigator at most 4 hours; at most 12M reported tokens where tokens are reported; at most USD 100 of incremental paid usage, all of it explicitly authorized; report within 3 days of preregistration |

Outcome labels, decided by `assess.py`:
- **Useful**: C1 through C7 all met.
- **Partially useful**: C1 and C2 met, and at least two of C3, C4 and C5 met.
- **Not demonstrated**: anything else.

Separately from those labels:
- Code Witness's own verification outcome for the baseline is reported exactly as the engine produced it. A legacy-only baseline is INCONCLUSIVE by design, which does not fail any criterion.
- Coverage, mutation scores and challenge results never turn into PASS or FAIL. Coverage has **no threshold** and is reported beside the criteria.
- The owner may later set coverage or mutation thresholds for a real migration decision. This experiment does not.

## 2. Mutant eligibility, failure classification and denominators

These rules are fixed before execution and apply identically to both suites.

**Scope.** Mutants are generated only in the target scope: the target module and
the in-repo modules it imports, as listed in `PREREG.json`. They mutate the
actual target source files, never a copy held by the adapter.

**Identical mutations.**
- Each mutant is applied once with `cosmic-ray apply`, and `git diff` is hashed.
- Both suites run one after the other against that same tree. The diff hash is checked before restoration, so both see byte-identical mutated source.
- Restoration is `git checkout`, then `git clean -fd`, then a clean-tree check, and it runs even after a failure.
- Bytecode caches are purged before every suite run, and `PYTHONDONTWRITEBYTECODE=1` is set.

**Sampling.** All mutants are enumerated. If there are more than 400, a sample
of 400 is drawn with the preregistered seed (`score.py mutants --seed`). The
sample is the same for both suites, and each mutant has a stable id
`path:operator:occurrence`.

**Validity** (decided before either suite runs, the same for both suites):

| Validity | Rule | Treatment |
| --- | --- | --- |
| `not-applied` | `cosmic-ray apply` failed or produced no diff | Excluded from every denominator; counted |
| `non-compiling` | A changed file no longer compiles | Excluded; counted |
| `import-failure` | Importing the target-scope modules fails or exceeds 30 s | Excluded; counted |
| `valid` | Everything else | Scored |

**Upstream failure classification.**
- `score.py` runs pytest with `--tb=long --junitxml` and classifies every failing test from the junit report.
- Each `<failure>` is classified by the exception type and the location on the last traceback line (`path:line: Type`):

| Test result | Class | Counts as a kill |
| --- | --- | --- |
| `AssertionError`, or pytest's `Failed` (for example DID NOT RAISE) | `assertion` | Yes |
| Any other exception whose last frame is in a target-scope file | `target-exception` | Yes |
| `ImportError` or `ModuleNotFoundError` | `dependency` | No (error) |
| `<error>` during collection | `collection` | No (error) |
| `<error>` during setup or teardown | `setup` | No (error) |
| Any other failure, or no parseable location | `unclassified` | Only if the adjudicator records `behavioral` |

**Per-suite outcome** for each valid mutant, in order of precedence:

| Outcome | Witness baseline | Upstream suite |
| --- | --- | --- |
| `behavioral` | At least one fixture observation differs from the frozen baseline | At least one `assertion` or `target-exception` test |
| `adjudicate` | n/a: the witness suite compares recorded observations | At least one `unclassified` test and no behavioral test |
| `timeout` | At least one case exceeded the engine's 5 s case limit | The suite exceeded its preregistered timeout |
| `error` | A case could not run (harness worker failure) | Only `dependency`, `collection` or `setup` results, or a nonzero exit with no test results |
| `survived` | None of the above | Suite passed |

An `error` result is rerun once. If it repeats, it stays `error`.

**What counts as a kill:**
- A suite kills a mutant only with `behavioral`, or with `adjudicate` followed by an adjudicated `behavioral` verdict.
- Timeouts, errors and uncertain failures are never kills. A mutant is never counted as killed because the test environment failed.

**Adjudication** (section 9.5):
- Every `adjudicate` outcome gets a `failure-classification` verdict (`behavioral`, `not-behavioral` or `indeterminate`).
- Every valid mutant that neither suite kills gets an `equivalence` verdict:
  - `equivalent`
  - `not-equivalent`, with a distinguishing input that the coordinator executes on the pristine and mutated trees
  - `indeterminate`
- Each verdict carries a written rationale.

**Primary denominator D** = valid mutants killed by at least one suite, plus
adjudicated `not-equivalent` mutants.
- Kill rate of each suite = that suite's kills within D, divided by D.
- C3 compares these two rates.
- C3 is not evaluable if any of these hold:
  - the recorded results do not match the sampled mutant ids exactly once each (a missing, duplicated or unexpected id; result order does not matter, so a resumed run is fine)
  - a survivor lacks an equivalence verdict
  - a failure classification is unresolved
  - D is empty
  - the S5 error share is exceeded

Reported separately, never folded into D or the rates:
- invalid mutants by validity class
- equivalent mutants
- indeterminate mutants
- timeouts, by suite
- persistent errors, by suite
- adjudicated failure classifications

Two secondary views are reported beside the primary rate:
- kills plus timeouts, divided by D
- an upper-bound denominator that also includes indeterminate mutants

**Fairness checks reported with the result:**
- per suite, the count of `error` outcomes and the median clean run time
- the upstream timeout, preregistered as the larger of 60 s and 10 times the median clean upstream run in preflight P4
- the fixed engine case timeout of 5 s

If either suite has persistent errors on more than 5% of valid mutants, stop
condition S5 applies before results are interpreted.

## 3. Held-out challenges: counts and validity

**Counts.**
- The challenger writes 14 regressions (`R01` to `R14`) and 14 behavior-preserving controls (`N01` to `N14`), so some can fail validation without dropping below the required counts.
- **Regressions.** The first 10 valid ones in ID order are scored; any further valid ones are reported but not scored.
- **Controls.** All valid controls are scored, and at least 10 are required.
- **Shortfall.** If either count falls short, one replacement round runs: a new fresh challenger session gets the same prompt, asking for the shortfall plus 2, with IDs continuing the sequence. It sees no earlier patches or results. If the count is still short, C4 or C5 is not evaluable.

**Regression valid** when all of these hold:
- it applies with `git apply --check`
- it changes only target-scope files
- its `exposing_input` snippet (or one the adjudicator supplies) gives a different result on the pristine and patched trees when the coordinator executes both, with the outputs recorded

**Control valid** when all of these hold:
- it applies and changes only target-scope files
- the upstream suite passes with it applied
- the adjudicator reads the diff and records, with a rationale, that it does not change any return value, exception type or message, or output

Validity is recorded as `challenge-validity` verdicts before any challenge is scored.

**False alarm.** A valid control that the baseline flags (`behavioral`) goes to
the adjudicator together with the differing observation:
- `behavior-changed`: the control is removed from the control count and reported as reclassified, not scored in C4.
- `false-alarm`: counts against C5.
- `indeterminate`: also counts against C5. Uncertainty does not favor the baseline.

Conditions that make C4 and C5 not evaluable:
- A flagged control without a dispute verdict makes C5 not evaluable.
- A valid control on which the baseline did not run to an outcome (`timeout`, `error` or `adjudicate`) is untested and makes C5 not evaluable. An untested control can never count as "no false alarm".
- Challenge results must match the scored challenge ids exactly once each, or C4 and C5 are not evaluable.
- A regression on which the baseline times out or errors counts as not detected.

## 4. Budgets, interventions and stop conditions

Budgets are ceilings, not targets.

**Aggregate ceilings:**
- **Agent-hours:** 12, measured as the wall-clock time of every agent session: coordinator, investigator, challenger, adjudicator, P1 probe sessions and replacement rounds.
- **Investigator:** at most 4 hours, one session, at most 2 restarts after runtime crashes.
- **Reported tokens:** 12 million in total, where the runtime reports them. Codex: `input_tokens + output_tokens` from each `turn.completed` event. Claude Code: input, cache-creation, cache-read and output tokens from each `result` event. Sessions that report no tokens are listed as a measurement gap, and the other limits are still enforced.
- **Incremental paid usage:** at most USD 100. No API purchase, paid credit or usage-based billing may be started without explicit owner authorization, and any actual charge must be recorded with that authorization. Claude Code's `total_cost_usd` is an API-equivalent estimate, recorded only as `estimated_api_equivalent_usd_not_a_charge`. It is never reported as a cost of a subscription session.
- **Calendar:** 3 days from preregistration to the last agent session.
- **Owner attention:** at most 8 interventions and at most 45 minutes in total.
- **Scorer compute** (not agent time): at most 6 hours across mutants, coverage, knockout and challenges.

**Planning allocation within the 12 agent-hours:** investigator 4, challenger
1.5 (including a replacement round), adjudicator 2, coordinator 4.5. Only the
investigator cap and the aggregate are criteria.

**Usage records.**
- Each agent session is one row in `USAGE.jsonl`, produced by `assess.py usage` from the session's own machine-readable event log.
- The coordinator adds the start and end times, taken from `date -u` immediately before and after the launch command, and the restart count.
- Tracked per row: tokens, model invocations (turns), elapsed time, restarts, any actual incremental charge, and whether it was authorized.

**Intervention log.** Every human action is a row in `INTERVENTIONS.jsonl`:
`time`, `phase`, `role`, `category`, `initiated_by`, `minutes`, `description`, `effect`.
- Categories: `clarification`, `approval`, `login`, `troubleshooting`, `manual-repair`, `test-design`, `code-explanation`, `other`.
- Every clarification, approval, sign-in, permission prompt, troubleshooting step and manual repair counts.
- A manual repair of any investigator or challenger artifact, by a human or by the coordinator, is contamination (S4), not a repair.

**Incident log.** Every stop condition that fires is a row in `INCIDENTS.jsonl`
(`condition`, `time`, `description`, `evidence`). `assess.py` treats any S3, S4
or S7 row as invalidating.

**Stop conditions**
- **S1 Role budget exhausted.**
  - Investigator: freeze whatever exists and score it. If no pack exists, the outcome is "Not demonstrated: no baseline produced".
  - Challenger: score the valid challenges that exist; C4 or C5 may be not evaluable.
  - Adjudicator or scorer: stop and report what is complete.
- **S2 Aggregate budget exhausted.** Any aggregate ceiling in this section is reached. Stop and report partial results; C7 is not met.
- **S3 Isolation invalid.** A preflight failure blocks the experiment until it is fixed and preflight passes again from the start. During a run, any evidence that a role could read, write or reach something outside its boundary, or that credentials were exposed, invalidates the run. Do not rerun on the same target; the owner decides on a new one. Isolation is never weakened to proceed.
- **S4 Contaminated evaluation.** Any exposure of withheld material to the investigator or challenger, any recovery of upstream tests, any edit of a role's artifacts by someone other than that role, or any change to preregistered material after freeze. Stop and mark the run invalid.
- **S5 Repeated failures.** Any of the following:
  - the same tooling or infrastructure failure occurring twice
  - a tree left dirty after restoration
  - more than 2 investigator runtime restarts
  - persistent errors on more than 5% of valid mutants for either suite
  - a role session that fails to start twice
  Stop that phase, record the failure and its evidence, and report. A first occurrence may be retried once after the cause is recorded.
- **S6 Engine limitation.** If the investigator is blocked by a Code Witness limitation, it works around it in its adapter or records it and freezes. The engine is not changed during the run. The limitation becomes a finding.
- **S7 No tuning after freeze.** After freeze, the baseline, fixtures, adapter, criteria, thresholds, denominators, scripts, seeds, timeouts and challenge prompts do not change, whatever the results show. Any departure is recorded in `INCIDENTS.jsonl` and `DEVIATIONS.md`, and `assess.py` reports the run as not valid.

## 5. Target selection (coordinator)

Required properties:
- Public repository under an MIT, BSD or Apache-2.0 license, not owned by Stephen, and not previously used with Code Witness (this excludes `fm_voice_frame.py` and the vendored HTTP helper).
- Fewer than 1,000 GitHub stars, to reduce the chance the models have memorized its tests. Record the star count; this risk is reduced, not removed.
- Pure Python, with runtime dependencies from the standard library only (vendored modules count as in-repo). Supports CPython 3.13.
- A **target module** of 150 to 600 source lines of deterministic logic (parsing, formatting, validation, conversion, calculation) that imports at least one in-repo helper module.
- The target scope does not use the network, subprocesses, filesystem writes, wall-clock time or randomness, or those effects can be avoided through its public API. Check with a grep for `socket`, `subprocess`, `urllib`, `http`, `requests`, `os.system`, `shutil`, `open(` with write modes, `time.`, `datetime.now`, `random`, `threading` and `asyncio`, and read every hit.
- An existing test suite that pytest can run (pytest also runs unittest suites), that exercises the target module, passes at the pinned SHA, and finishes in under 2 minutes.

Procedure:
1. Find up to 5 candidates through GitHub search and PyPI. For each, record the URL, SHA, stars, license, target module, its source lines and helpers, test command, test runtime, and the upstream suite's line and branch coverage of the target scope.
2. Disqualify any candidate that fails a required property, and say why.
3. Pick the qualifying candidate whose upstream target-scope **line coverage is closest to 80%**. Tie-break: the smaller target module.
4. Record the table and the choice in `sealed/SELECTION.json`. Do not consult the owner. The target is never named in this repository before the report.

### 9.1 Investigation

Start the investigator with the role launch command that passed P1, from a fresh
session. Its only prompt is the brief below, saved as `BRIEF.md`:

```text
You are working in this directory only. It contains:
- repo/: the source of <project name> at a fixed revision. Its automated tests
  and their history have been removed. Do not try to recover them.
- .venv/: Python 3.13 with Code Witness installed (command: debt-compiler).
- CODE-WITNESS-README.md: Code Witness documentation.

Objective: Someone is about to change repo/<target module path>. Understand it,
and the repository code it depends on, well enough to establish a trustworthy
behavioral baseline, so that a future change that alters its observable
behavior is detected. Handle the investigation, scenario design, dependency
discovery and execution preparation yourself. Your baseline will later be
evaluated independently against changes you will not see. Clearly distinguish
what you have verified from what you are inferring.

Deliverables, all under repo/_witness/ (already excluded from git):
1. slice/legacy/batch.py: an adapter defining run(case, sleep=...) that calls
   the real repository code. It may convert inputs and outputs to JSON, but must

   using a path relative to this file.
2. slice/fixtures/cases.json: your scenarios, as literal JSON in the format the
   README describes.
3. pack/: the contract pack from
   .venv/bin/debt-compiler extract repo/_witness/slice/legacy/batch.py <target
   module and every repository module it imports that you want fingerprinted>
   --out repo/_witness/pack
   Set PYTHONDONTWRITEBYTECODE=1 for all runs.
4. BASELINE.md: what the scenarios cover, how the adapter maps inputs and
   outputs, and the behavior you know is not covered.
5. CLAIMS.md: one line per claim about the module's behavior, each tagged
   Observed, Inferred, Verified or Unknown, with a pointer to its evidence

6. FREEZE-READY: an empty file, created last, when you are finished.

Rules:
- Do not modify anything in repo/ outside repo/_witness/. Do not modify Code

  record it in BASELINE.md.
```

### 9.3 Challenges

Start the challenger with its P1-verified launch command, in `challenger/`, with
this prompt:

```text
repo/ is the source of <project name>. Its tests are removed; do not recover them.
Write 14 realistic maintenance regressions and 14 behavior-preserving changes to
repo/<target module path> and the repository modules it imports.

Regressions: the kind of mistake a competent maintainer could make during a
refactor or fix (boundary, default value, error handling, encoding, ordering,
state, type handling, missing case). Each one must change observable behavior

syntax errors, import failures or a function that always raises.

Behavior-preserving changes: refactors a maintainer might do (rename locals,
extract a helper, reorder independent statements, simplify an expression,

message, or output for any input.

For each, write challenges/<R01..R14 or N01..N14>.patch (a unified diff against
repo/, applying with git apply) and challenges/<id>.json with "category",

```

Then:
1. Copy `challenger/challenges/` to `sealed/challenges/` and record the hashes.
2. Audit the event log.
3. Validate each challenge under section 3 with the adjudicator.

### 9.4 Scoring

All scoring runs from `scoring/` through `contained` (see "Scoring sandbox").
`$S` stands for `.venv/bin/python tools/score.py`, `$SCOPE` for the
preregistered target-scope files, and `$UP` for the preregistered upstream pytest
argv as a JSON list. Outputs go to `scoring/evidence/` under the file names that
`assess.py` reads.

1. **Scoring tree.**
   - Clone the target at the pinned SHA into `scoring/tree`, outside the sandbox because cloning needs the network. This brings back the upstream tests.
   - Extract `sealed/baseline.tar` into `scoring/tree/_witness/` and add `_witness/` to `.git/info/exclude`.
   - Copy `baseline.tar`, `FREEZE.json`, `PREREG.json` and `PREFLIGHT.json` into `evidence/`.
   - Confirm every source fingerprint in `_witness/pack/manifest.json` matches the scoring tree. A mismatch stops scoring until it is explained (S5).
2. **Clean replay** (C2):
   `contained $S check --tree tree --scope $SCOPE --pack tree/_witness/pack --upstream "$UP" --upstream-timeout <prereg> --runs 3 > evidence/clean.json`.
   If upstream fails, stop: the selection was wrong.
3. **Coverage** (M2), measured separately per suite inside the sandbox:
   ```bash
   contained .venv/bin/coverage run --branch --data-file=cov-baseline --include='<target scope globs>' tools/fixture_coverage.py tree/_witness/slice/legacy/batch.py tree/_witness/slice/fixtures/cases.json
   contained /bin/bash -c "cd tree && ../.venv/bin/coverage run --branch --data-file=../cov-upstream --include='<target scope globs>' -m pytest -q -p no:cacheprovider <upstream test path>"
   contained .venv/bin/coverage combine --keep --data-file=cov-union cov-baseline cov-upstream
   ```
   Report all three with `coverage json --data-file=<file>`.
4. **Mutants** (C3):
   `contained $S mutants --tree tree --scope $SCOPE --seed <prereg seed> --out evidence/mutants.json`, then
   `contained $S run --tree tree --scope $SCOPE --pack tree/_witness/pack --upstream "$UP" --upstream-timeout <prereg> --mutants evidence/mutants.json --import-root <import root> --import-module <prereg modules> --out evidence/mutants.jsonl`.
   The scorer refuses to start a mutant on a dirty tree and restores the tree after every mutant, even on failure. Use `--start` and `--stop` to resume after an interruption, appending to the same file.
5. **Challenges** (C4, C5):
   `contained $S challenges --tree tree --scope $SCOPE --pack tree/_witness/pack --upstream "$UP" --upstream-timeout <prereg> --dir sealed-copy/challenges --ids <valid ids in ID order> --out evidence/challenges.jsonl`.
   Here `sealed-copy/` is a copy of the challenges inside `scoring/`. A regression is detected when the witness suite reports `behavioral`. Upstream results are reported beside it.
6. **Adapter honesty** (C2):
   `contained $S knockout --tree tree --scope $SCOPE --pack tree/_witness/pack > evidence/knockout.json`.
   - This replaces every target-scope function body with a raise and reports each fixture as `changed` (observation differs from the frozen baseline; `reached_target` counts those carrying the knockout exception), `unchanged`, `blocked` (timed out) or `errored` (harness could not run it).
   - Only `changed` counts toward the 80% threshold. If blocked or errored cases could decide the outcome, the status is `insufficient-evidence`, never `pass`.
   - Knockout alone cannot show the adapter does not also compute results itself, so the independent adapter review in 9.5 is always required.

### 9.5 Adjudication

The adjudicator works from packets prepared by the coordinator in `adjudicator/`.
Each packet contains only what the judgment needs. Every verdict is one row in
`evidence/ADJUDICATION.jsonl`:
`{"id", "question", "suite" (failure-classification only), "verdict", "rationale", "evidence", "confidence"}`.

| `question` | `id` | Allowed `verdict` |
| --- | --- | --- |
| `equivalence` | mutant id | `equivalent`, `not-equivalent` (with an executed distinguishing input), `indeterminate` |
| `failure-classification` | mutant id, with `suite` | `behavioral`, `not-behavioral`, `indeterminate` |
| `challenge-validity` | challenge id | `valid`, `invalid` |
| `control-dispute` | control id | `behavior-changed`, `false-alarm`, `indeterminate` |
| `adapter-reimplementation` | `adapter` | `none`, `reimplements`, `indeterminate` |
| `claim-calibration` | claim line number | `supported`, `unsupported`, `false` |

- **Equivalence packets** hold the mutant diff, the target-scope source and a runner for snippets on the pristine and mutated trees. Mutants are presented in random order with neutral IDs and no suite outcomes.
- **Failure-classification packets** hold the mutant diff and the failing test's junit text, but not the other suite's result.
- **Claims calibration.** Check up to 10 claims tagged `Verified` in `CLAIMS.md` (all of them if there are fewer; otherwise every k-th one in file order). No criterion is attached.

Uncertainty is kept, not resolved by default. `indeterminate` stays
`indeterminate` and is reported.

## Known limits of this design

- One target says little about the general case. The result is a data point and a list of failure modes, not a capability claim.
- Low star count reduces, but does not remove, the chance that models memorized the target or its tests.
- Mutation operators are syntactic. A high kill rate does not mean business-relevant behavior is covered, and equivalence and failure-classification verdicts are judgments, which is why their rationale and uncertainty are recorded.
- Upstream failure classification relies on pytest's junit format and the last traceback line. Anything it cannot place goes to adjudication, not to a kill.
- The challenger is an LLM. Its regressions approximate maintenance mistakes; they are not field defects.
- Knockout proves fixtures reach target functions. It cannot prove an adapter does not also compute outputs itself, which is why the adjudicator reviews the adapter.
- The witness suite's case timeout (5 s) is fixed by the engine and differs from the upstream suite's timeout. Timeouts are reported but never counted as kills.
- Runtime isolation was verified on this Mac with Codex CLI 0.163.0 and Claude Code 2.1.309. A runtime update can change any of it, which is why P1 runs immediately before preregistration.
- C1 depends on the coordinator recording incidents honestly. `assess.py` checks the hashes it can check and treats any recorded S3, S4 or S7 as invalidating, but it cannot detect an unrecorded incident.

## Mechanics evidence (October 23, 2026)

This evidence is about the scoring machinery and runtime isolation only, not about the experiment.

**Pilot on a scratch copy of the v0.3 voice-frame codec** (its 25 existing
fixtures were written with knowledge of the code, so this is not baseline evidence):
- A legacy-only baseline (INCONCLUSIVE, exit 0) replays clean and fails when the imported module is mutated in place. No modern copy is needed for mutation scoring.
- **Stale bytecode masks mutants.** A same-size `>` to `<` edit with an unchanged mtime passed replay while `__pycache__` held the old `.pyc`, and failed with 14 failing subtests after the cache was purged.
- **cosmic-ray does not run `test-command` through a shell.** A command written as `rm -rf <dir> && ...` passed every later word to `rm` and deleted pilot files. The scorer therefore never uses `cosmic-ray exec`.
- The fixtures covered 100% of the codec's lines and branches, yet 7 of 73 mutants survived.

**Canary preflight** (`preflight_canary.sh`, Code Witness wheel built from `5cc6ea7`, CPython 3.13.16, macOS arm64):
- All 13 checks passed, both unsandboxed and inside the Codex permission-profile scoring sandbox, with identical summaries and identical per-mutant diffs and outcome classes.
- 66 of 66 mutants were valid. Witness suite: 52 behavioral, 10 timeouts, 4 survived. Upstream suite: 25 behavioral, 41 survived. Target exceptions were classified and nothing was unclassified.
- A missing upstream test path was classified as `error`, not a kill.
- The stale-bytecode edit was detected with the purge, while the control without the purge was masked.
- Knockout: `pass` with the honest adapter (12 of 12 changed), `fail` with the dishonest one (0 changed).
- The tree was clean and the sentinels outside it were intact afterward.
- Earlier runs of the previous scorer version were also deterministic across two runs and passed inside a `sandbox-exec` profile. That profile allowed reads of credential files, so it is replaced by the Codex permission profile.
