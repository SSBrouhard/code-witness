# Code Witness v0.4: blind baseline experiment protocol

Status: draft for owner approval. Nothing in this document has been executed
against a real target.
Task: [PORT-110](https://linear.app/stephen-portfolio/issue/PORT-110/write-code-witness-v04-blind-baseline-experiment-protocol).
Written October 23, 2026, America/New_York. Follows the v0.3 real-world validation (PORT-105).

Supporting materials: [`experiments/v0.4-blind-baseline/`](../experiments/v0.4-blind-baseline/)
holds the deterministic scorer, the isolation probe, the fixture coverage
runner and a committed canary used only for preflight. None of it is part of the
`debt-compiler` engine.

## Question

Can an independent coding agent, given only an unfamiliar repository and an
objective, use Code Witness to build a behavioral baseline that detects changes
it was never told about, and how does that baseline compare with the
repository's own test suite on the same changes?

This is one experiment on one target. It is not a framework, a benchmark suite
or a product release. Its result decides what, if anything, the engine needs next.

## Fixed constraints

1. One independent target.
2. Investigator, challenger, adjudicator and scorer are separate roles with enforced information boundaries.
3. Acceptance criteria, denominators, budgets and stop conditions are fixed by this document and the preregistration before the investigator starts.
4. The baseline is frozen and hashed before any challenge or mutant list exists.
5. The baseline and the upstream suite are scored against byte-identical mutations of the actual target implementation.
6. Code Witness verification outcomes (PASS / FAIL / BLOCKED / INCONCLUSIVE), coverage, mutation detection, held-out regressions, false alarms, missing evidence, human intervention and cost are reported as separate measures. None of them changes another, and there is no combined score.
7. A failed safety or integrity preflight blocks the experiment until resolved. Isolation is never weakened to make the experiment run.
8. Nothing is tuned after freeze: fixtures, adapter, criteria, thresholds, denominators, scripts, seeds, timeouts and the challenge set stay as preregistered.
9. No Code Witness engine changes, security remediation, production actions, publication or pushes during the experiment. Withheld evaluation material is never committed to this public repository.

Anyone who follows this protocol must not need the owner to design tests, choose
mutations, pick the target or explain code. The owner's planned actions are
approving this document, any approvals listed in "Decisions for owner approval",
logging in agent runtimes when required, and reading the final report. Each of
these is logged as an intervention (section 4).

## Phases

| Phase | Owner of the step | Output |
| --- | --- | --- |
| 0. Approval | Owner | This protocol merged or explicitly accepted at a commit SHA |
| 1. Target selection | Coordinator | Selection table (sealed) |
| 2. Setup | Coordinator | Role workspaces, pinned wheel, stripped repo |
| 3. Preflight P1 to P6 | Coordinator | `PREFLIGHT.json`; any failure blocks |
| 4. Preregistration | Coordinator | `PREREG.json`, SHA-256 posted to PORT-110 |
| 5. Investigation | Investigator | Baseline under `repo/_witness/` |
| 6. Freeze | Coordinator | `baseline.tar`, `FREEZE.json`, SHA-256 posted to PORT-110 |
| 7. Challenges | Challenger, then adjudicator | Validated regressions and controls |
| 8. Scoring | Scorer (deterministic) | Mutant results, coverage, challenge results |

| 10. Report | Coordinator | `REPORT.md`, `results.json`, evidence |

has produced its output.

## Roles and boundaries

| Role | Who | Sees | Never sees |
| --- | --- | --- | --- |
| Coordinator | One agent session (Codex or Claude Code). Runs setup, preflight, the scorer and the report. | Everything | Does not edit role artifacts after they are handed in |
| Investigator | Fresh session with no prior context, started from the brief in section 9.1 only | Its workspace: the target repo with tests and test history removed, the pinned Code Witness wheel and its README | This protocol, the preregistration, upstream tests, mutants, challenges, other role workspaces, other sessions' transcripts, the network |
| Challenger | Fresh session, a **different model family** from the investigator if one is available | Its own copy of the stripped repo | The baseline, upstream tests, mutants, scoring rules, other sessions' transcripts |
| Adjudicator | Fresh session with no prior context | Only the packet it is given for each judgment | Which suite killed what, and the investigator's artifacts unless a dispute requires them |
| Scorer | `experiments/v0.4-blind-baseline/score.py`, run by the coordinator | Frozen baseline, pristine repo, mutants, challenges | n/a (no judgment) |
| Owner | Stephen | The final report, plus the approvals listed in this document | Is never asked to design tests, choose scenarios or explain code |

Boundaries are enforced in two ways, and preflight must demonstrate both (P1, P6):

- **Ordering.** Upstream tests and their history are removed from the investigator's repo, and the coordinator's pristine clone is deleted before the investigator starts. Mutant lists, challenger patches and negative controls are created only after freeze. Nothing withheld exists on disk while the investigator works, except sealed coordinator files, which isolation must make unreadable.
- **Isolation.** The investigator, challenger and adjudicator run with commands that have no network access, writes limited to their own workspace, and **reads denied** outside their workspace, the agent runtime's own installation and the operating system. This includes other role directories, `~/Projects`, the coordinator's sealed files and every agent runtime's session history (for example `~/.claude` and `~/.codex`). If a runtime has file tools that bypass its command sandbox, the whole runtime process must run inside the isolation boundary. A runtime that cannot meet this is not used.

Acceptable isolation mechanisms, in order of preference:
1. A macOS `sandbox-exec` profile around the entire agent runtime process that denies file reads and writes outside the allowed paths, combined with the runtime's own command sandbox for network denial. The runtime uses a fresh state directory (for example `CODEX_HOME`) inside the role's area, so earlier transcripts are not reachable.
2. A separate macOS user account whose home contains only that role's workspace.
3. A cloud agent session whose only repository is a private copy of that role's workspace, with network disabled for commands.

Mechanisms 2 and 3 require owner approval (account creation, or pushing a private
repository), so they appear under "Decisions for owner approval". Whichever is
used must pass P1. If none passes, the experiment is blocked.

## 1. Acceptance criteria

Each criterion is reported separately as met / not met / not evaluable, with the
numbers behind it. "Not evaluable" counts as not met.

| ID | Criterion | Threshold |
| --- | --- | --- |
| C1 | Valid run | Preflight passed; no isolation or contamination stop fired (S3, S4); no post-freeze tuning (S7) |
| C2 | Baseline integrity | Extraction is not BLOCKED; clean replay passes 3 of 3; knockout changes the observations of at least 80% of fixtures; the adjudicator finds no reimplementation of target logic in the adapter (sections 9.4 step 6 and 9.5) |
| C3 | Mutation detection versus upstream | On the primary mutant denominator (section 2), the baseline's behavioral kill rate is at least the upstream suite's rate minus 10 percentage points. "Exceeds upstream" is reported when it is higher. |
| C4 | Held-out regressions | Exactly 10 valid, independently developed regressions are scored, and the baseline detects at least 7 |
| C5 | False alarms | At least 10 valid behavior-preserving controls are scored, and the baseline fails at most 1 of them |
| C6 | Supervision | Zero interventions in the test-design or code-explanation categories in any role, and the operator-attention budget is respected (section 4) |
| C7 | Cost | Every role budget and every aggregate budget in section 4 is respected |

Outcome labels, decided mechanically:
- **Useful**: C1 through C7 all met.
- **Partially useful**: C1 and C2 met, and at least two of C3, C4 and C5 met.
- **Not demonstrated**: anything else.

Separately from those labels:
- Code Witness's own verification outcome for the baseline is reported exactly as the engine produced it. A legacy-only baseline is INCONCLUSIVE by design, which does not fail any criterion. Coverage, mutation scores and challenge results never turn into PASS or FAIL.
- Coverage has **no threshold**. It is reported beside the criteria so that a PASS is never read as "well covered".
- The owner may later set coverage or mutation thresholds for a real migration decision. This experiment does not.

## 2. Mutant eligibility and denominators

These rules are fixed before execution. The scorer applies them mechanically,
and the adjudicator decides only the questions marked for adjudication.

**Scope.** Mutants are generated only in the target scope: the target module and
the in-repo modules it imports, as listed in `PREREG.json`. They mutate the
actual target source files, never a copy held by the adapter.

**Identical mutations.** For each mutant, the scorer applies the mutation once
with `cosmic-ray apply`, hashes `git diff`, runs both suites one after the other
against that same working tree, and confirms the diff hash is unchanged before
it restores the tree. Both suites therefore see byte-identical mutated source.
Bytecode caches are purged before every suite run, and `PYTHONDONTWRITEBYTECODE=1` is set.

**Sampling.** All mutants are enumerated. If there are more than 400, a sample
of 400 is drawn with the preregistered seed (`score.py mutants --seed`). The
sample is the same for both suites.

**Validity** (decided before either suite runs, the same for both suites):

| Validity | Rule | Treatment |
| --- | --- | --- |
| `not-applied` | `cosmic-ray apply` failed or produced no diff | Excluded from every denominator; counted |
| `non-compiling` | A changed file no longer compiles | Excluded; counted |
| `import-failure` | Importing the target-scope modules fails or exceeds 30 s | Excluded; counted |
| `valid` | Everything else | Scored |

**Per-suite outcome** for each valid mutant:

| Outcome | Witness baseline | Upstream suite |
| --- | --- | --- |
| `behavioral` | At least one fixture observation differs from the frozen baseline | At least one test reports a failure (pytest junit `<failure>`) |
| `timeout` | No difference, but at least one case exceeded the engine's 5 s case limit | The suite exceeded its preregistered timeout |
| `error` | No difference or timeout, but a case could not run (harness worker failure) | Errors only: collection or setup `<error>`, or a nonzero exit with no failures |
| `survived` | None of the above | Suite passed |

An `error` result is rerun once. If it repeats, it stays `error`. **Only
`behavioral` counts as a kill.** A mutant is never counted as killed because the
test environment failed, and a timeout is never counted as a kill in the primary rate.

**Adjudication.** Every valid mutant that neither suite kills behaviorally goes
to the adjudicator (section 9.5), who records `equivalent`, `not-equivalent` or
`indeterminate` with a written rationale. `not-equivalent` needs a distinguishing
input that the coordinator executes on the pristine and mutated trees, with the
outputs recorded.

**Primary denominator D** = valid mutants killed behaviorally by at least one
suite, plus adjudicated `not-equivalent` mutants.
- Kill rate of each suite = that suite's behavioral kills within D, divided by D.
- C3 compares these two rates.

Reported separately, never folded into D or the rates:
- invalid mutants by validity class
- equivalent mutants
- indeterminate mutants
- timeouts, by suite
- persistent errors, by suite

Two secondary views are reported beside the primary rate:
- behavioral kills plus timeouts, divided by D
- an upper-bound denominator that also includes indeterminate mutants

**Fairness checks reported with the result:**
- per suite, the count of `error` outcomes and the median clean run time
- the upstream timeout, preregistered as the larger of 60 s and 10 times the median clean upstream run in preflight P4
- the fixed engine case timeout of 5 s

If either suite has persistent errors on more than 5% of valid mutants, stop
condition S5 applies before results are interpreted.

## 3. Held-out challenges: counts and validity

**Counts.**
- The challenger writes 14 regressions (`R01` to `R14`) and 14 behavior-preserving controls (`N01` to `N14`), so some can fail validation without dropping below the required counts.
- **Regressions.** The first 10 valid ones in ID order are scored; any further valid ones are reported but not scored.
- **Controls.** All valid controls are scored, and at least 10 are required.
- **Shortfall.** If either count falls short, one replacement round runs: a new fresh challenger session gets the same prompt asking for the shortfall plus 2. It sees no earlier patches or results. If the count is still short, C4 or C5 is not evaluable.

**Regression valid** when all of these hold:
- it applies with `git apply --check`
- it changes only target-scope files
- its `exposing_input` snippet (or one the adjudicator supplies) gives a different result on the pristine and patched trees when the coordinator executes both, with the outputs recorded

**Control valid** when all of these hold:
- it applies and changes only target-scope files
- the upstream suite passes with it applied
- the adjudicator reads the diff and records, with a rationale, that it does not change any return value, exception type or message, or output

Valid counts and their rationale are frozen in `sealed/CHALLENGES.json` before
any challenge is scored.

**False alarm.** A valid control that the baseline flags (`behavioral`) goes to
the adjudicator together with the differing observation:
- If the control did change observable behavior, it is reclassified as a regression (reported, not scored in C4) and removed from the control count.
- Otherwise it counts as a false alarm.

## 4. Budgets, interventions and stop conditions

**Role budgets**

| Role | Wall-clock cap | Usage cap |
| --- | --- | --- |
| Investigator | 4 hours, one session, at most 2 restarts after runtime crashes | 10M tokens as reported by its runtime |
| Challenger | 1 hour, plus 30 minutes for a replacement round | 2M tokens, plus 1M for a replacement round |
| Adjudicator | 2 hours across all sessions | 3M tokens |
| Coordinator | 8 hours across selection, setup, preflight, scoring and report | 10M tokens |
| Scorer compute | 6 hours across mutants, coverage and challenges | n/a |

**Aggregate budgets** (all roles together):
- 30M tokens
- 16 hours of agent wall-clock time
- USD 200 of reported or list-price-equivalent model cost (if no runtime reports cost, the token cap governs)
- 3 calendar days from preregistration to report
- Operator attention: at most 8 interventions and 45 minutes of owner time in total, at most 2 interventions during the investigation phase, and zero in the test-design or code-explanation categories

If a runtime cannot report tokens or cost, record wall-clock time, turn count and
whatever usage it shows, and say so in the report.

**Intervention log.** Every human action is a row in `sealed/INTERVENTIONS.jsonl`:
`time`, `phase`, `role`, `category`, `initiated_by`, `minutes`, `description`, `effect`.
- Categories: `clarification`, `approval`, `login`, `troubleshooting`, `manual-repair`, `test-design`, `code-explanation`, `other`.
- Approvals of this protocol, runtime logins, permission prompts and environment fixes all count.
- A manual repair of any investigator or challenger artifact, by a human or by the coordinator, is contamination (S4), not a repair.

**Stop conditions**
- **S1 Role budget exhausted.**
  - Investigator: freeze whatever exists and score it. If no pack exists, the outcome is "Not demonstrated: no baseline produced".
  - Challenger: score the valid challenges that exist; C4 or C5 may be not evaluable.
  - Adjudicator or scorer: stop and report what is complete.
- **S2 Aggregate budget exhausted.** Stop. Report partial results with the label "Not demonstrated: budget exhausted".
- **S3 Isolation invalid.** A preflight failure blocks the experiment until it is fixed and preflight passes again from the start. During a run, any evidence that a role could read, write or reach something outside its boundary invalidates the run. Do not rerun on the same target; the owner decides on a new one. Isolation is never weakened to proceed.
- **S4 Contaminated evaluation.** Any exposure of withheld material to the investigator or challenger, any recovery of upstream tests, any edit of a role's artifacts by someone other than that role, or any change to preregistered material after freeze. Stop and mark the run invalid.
- **S5 Repeated failures.** The same tooling or infrastructure failure occurring twice, a tree left dirty after restoration, more than 2 investigator runtime restarts, or persistent errors on more than 5% of valid mutants for either suite. Stop that phase, record the failure and its evidence, and report. A first occurrence may be retried once after the cause is recorded.
- **S6 Engine limitation.** If the investigator is blocked by a Code Witness limitation, it works around it in its adapter or records it and freezes. The engine is not changed during the run. The limitation becomes a finding.
- **S7 No tuning after freeze.** After freeze, the baseline, fixtures, adapter, criteria, thresholds, denominators, scripts, seeds, timeouts and challenge prompts do not change, whatever the results show. Any departure is a protocol deviation: it is recorded in `DEVIATIONS.md` and the run is labelled "Not demonstrated: deviated from protocol" unless the deviation demonstrably cannot affect any measure.

## 5. Target selection (coordinator)

Required properties:
- Public repository under an MIT, BSD or Apache-2.0 license, not owned by Stephen, and not previously used with Code Witness (this excludes `fm_voice_frame.py` and the vendored HTTP helper).
- Fewer than 1,000 GitHub stars, to reduce the chance the models have memorized its tests. Record the star count; this risk is reduced, not removed.
- Pure Python, with runtime dependencies from the standard library only (vendored modules count as in-repo). Supports CPython 3.13.
- A **target module** of 150 to 600 source lines of deterministic logic (parsing, formatting, validation, conversion, calculation) that imports at least one in-repo helper module.
- The target scope does not use the network, subprocesses, filesystem writes, wall-clock time or randomness, or those effects can be avoided through its public API. Check with a grep for `socket`, `subprocess`, `urllib`, `http`, `requests`, `os.system`, `shutil`, `open(` with write modes, `time.`, `datetime.now`, `random`, `threading` and `asyncio`, and read every hit.
- An existing test suite that pytest can run (pytest also runs unittest suites), that exercises the target module, passes at the pinned SHA, and finishes in under 2 minutes.

Procedure:
1. Find up to 5 candidates through GitHub search and PyPI. For each, record the URL, SHA, stars, license, target module, its source lines and helpers, test command, test runtime, and the upstream suite's line and branch coverage of the target scope.
2. Disqualify any candidate that fails a required property, and say why.
3. Pick the qualifying candidate whose upstream target-scope **line coverage is closest to 80%**. Tie-break: the smaller target module.
4. Record the table and the choice in `sealed/SELECTION.json`. Do not consult the owner. The target is never named in this repository before the report.

## 6. Setup (coordinator)

The experiment root is `~/cw-v04/`, outside `~/Projects`, with `sealed/`,
`investigator/`, `challenger/`, `adjudicator/` and `scoring/`. The final
evidence goes to `~/Projects/code-witness/outputs/v0.4-blind-baseline/`, which
stays local and is never committed.

1. **Pinned wheel.** From a clean checkout of the approved Code Witness commit, run `uv build --wheel`. Record the commit and the wheel's SHA-256. Roles install the wheel, never an editable checkout, so `docs/` and `experiments/` are not part of what they can import or read.
2. **Scoring environment.** Create `scoring/.venv` with Python 3.13 and install the wheel, `cosmic-ray==8.7.0`, `coverage==7.17.0`, `pytest==9.1.1` and the target's test dependencies. Record exact versions. Copy `experiments/v0.4-blind-baseline/` from the approved commit to `scoring/tools/` and record its file hashes.
3. **Pristine checks.** Clone the target at the pinned SHA into `sealed/pristine`. Run its suite 3 times, record the median run time, and measure upstream target-scope coverage for the selection table. Run preflight P4 there.
4. **Stripped repo.** Clone again into `investigator/repo`. Find every test path in the whole history (`git log --all --name-only --format= | sort -u`, then pick paths matching `test*`, `*_test.py`, `conftest.py` or directories named `test`/`tests`), and remove them from all history:
   ```bash
   git filter-branch --force --index-filter 'git rm -r -q --cached --ignore-unmatch <paths>' --prune-empty -- --all
   ```
   Then delete the remote, `refs/original`, tags pointing at removed history and the reflog, and run `git gc --prune=now --aggressive`. Doctests inside source docstrings stay, because they are part of the source; note whether the target has any.
5. **Investigator workspace.** In `investigator/`:
   - create `.venv` with Python 3.13 and install the wheel
   - copy the Code Witness `README.md` to `CODE-WITNESS-README.md`
   - add `_witness/` to `repo/.git/info/exclude`
   - save the brief from section 9.1 as `BRIEF.md`
   - create a fresh runtime state directory for the investigator's agent
   Nothing else goes in.
6. **Challenger workspace.** Copy the stripped `repo` to `challenger/repo`, create a `.venv` with Python 3.13 and no Code Witness, and create a fresh runtime state directory.
7. **Delete `sealed/pristine`** after P4. It is re-cloned by SHA only after freeze.

## 7. Preflight (blocking)

Preflight runs after setup and before preregistration. Every check writes
evidence to `sealed/preflight/` and a pass/fail line to `sealed/PREFLIGHT.json`.
Any failure blocks the experiment until it is resolved and **all** checks pass
again in a fresh run. A check is never skipped, and isolation is never weakened
to make a check pass.

| ID | Demonstrates | How | Passes when |
| --- | --- | --- | --- |
| P1 | Enforced workspace and network isolation | For each of the investigator, challenger and adjudicator: start a throwaway session in the exact runtime, sandbox and state directory the role will use, and have it run `python probe.py --workspace <role dir> --deny-read <paths> --deny-write <paths>`. The deny lists must include every other role directory, `sealed/`, `scoring/`, `~/Projects`, `~/Documents`, `~/.ssh` and every agent runtime's session history. Then ask the same session to read `sealed/SENTINEL.txt` (a random token) with its native file tool. Discard the probe session's state afterward. | `probe.py` exits 0, with every deny path existing and denied, workspace read and write allowed, and network denied for the process and a child process. The sentinel token does not appear anywhere in the probe transcript. |
| P2 | Safe execution of scoring scripts | `shellcheck preflight_canary.sh`, then `preflight_canary.sh <scoring venv> <new dir>`. Cosmic-ray is used only for `init`, `dump` and `apply`; it never executes a test command, and no scorer command goes through a shell. | Shellcheck is clean, and the canary's `tree restored` and `sentinels outside the tree intact` checks pass |
| P3 | Bytecode-cache handling prevents stale observations | Canary stale-bytecode check: warm the cache, make a same-size edit with the original mtime, then score | `stale-bytecode edit is detected` passes. The informational control without a purge is recorded. |
| P4 | Source restoration after mutation, on the actual target | Canary checks, plus `score.py mutants` and `score.py run --suites upstream --stop 10` on `sealed/pristine` | Canary restoration passes; the pristine tree is clean after all 10 runs; outcome classes are recorded; then the mutant list and results are deleted together with the pristine clone |
| P5 | The adapter check detects reimplementation | Canary knockout, run with an honest adapter and a dishonest one | `honest adapter: every fixture reaches target code` and `dishonest adapter: no fixture reaches target code` pass |
| P6 | No investigator access to withheld material | Test paths absent from `git log --all --name-only` and from `git count-objects -v` garbage in `investigator/repo` and `challenger/repo`; a listing with hashes of both workspaces matches the allowed contents in section 6; no mutant list, challenge or pristine clone exists under `~/cw-v04/`; P1's deny list covers `sealed/` and the coordinator's session history | All conditions hold |

The canary (`experiments/v0.4-blind-baseline/canary/`) is a tiny committed package
with a deliberately incomplete upstream test. It exists only to prove that the
scoring machinery behaves correctly. It is not an experiment target, and its
results are not experiment evidence.

## 8. Preregistration

After preflight passes, the coordinator writes `sealed/PREREG.json` and posts its
SHA-256 as a comment on PORT-110 **before the investigator starts**. The comment
timestamp is the external commitment. `PREREG.json` never changes afterward.

`PREREG.json` contains:
- **This protocol:** its commit SHA and the hashes of `experiments/v0.4-blind-baseline/`.
- **Pinned tools:** the Code Witness commit and wheel SHA-256.
- **Target:** URL, pinned SHA, target scope files, importable module names and the upstream pytest argv.
- **Runtimes:** the runtimes, models and isolation mechanism for each role.
- **Scoring parameters:** budgets (section 4), the mutation seed, the 400-mutant cap and the upstream timeout.
- **Evidence:** the SHA-256 of `SELECTION.json` and `PREFLIGHT.json`.

The public PORT-110 comment carries only the hash. The file stays in `sealed/`.

## 9. Execution

### 9.1 Investigation

Start the investigator in a fresh session in `investigator/`, inside the isolation
boundary that passed P1. Its only prompt is the brief below, saved as `BRIEF.md`:

```text
You are working in this directory only. It contains:
- repo/: the source of <project name> at a fixed revision. Its automated tests
  and their history have been removed. Do not try to recover them.
- .venv/: Python 3.13 with Code Witness installed (command: debt-compiler).
- CODE-WITNESS-README.md: Code Witness documentation.

Objective: Someone is about to change repo/<target module path>. Understand it,
and the repository code it depends on, well enough to establish a trustworthy
behavioral baseline, so that a future change that alters its observable
behavior is detected. Handle the investigation, scenario design, dependency
discovery and execution preparation yourself. Your baseline will later be
evaluated independently against changes you will not see. Clearly distinguish
what you have verified from what you are inferring.

Deliverables, all under repo/_witness/ (already excluded from git):
1. slice/legacy/batch.py: an adapter defining run(case, sleep=...) that calls
   the real repository code. It may convert inputs and outputs to JSON, but must
   not reimplement the target's logic. Add the repository root to sys.path
   using a path relative to this file.
2. slice/fixtures/cases.json: your scenarios, as literal JSON in the format the
   README describes.
3. pack/: the contract pack from
   .venv/bin/debt-compiler extract repo/_witness/slice/legacy/batch.py <target
   module and every repository module it imports that you want fingerprinted>
   --out repo/_witness/pack
   Set PYTHONDONTWRITEBYTECODE=1 for all runs.
4. BASELINE.md: what the scenarios cover, how the adapter maps inputs and
   outputs, and the behavior you know is not covered.
5. CLAIMS.md: one line per claim about the module's behavior, each tagged
   Observed, Inferred, Verified or Unknown, with a pointer to its evidence
   (fixture name, source line or pack file).
6. FREEZE-READY: an empty file, created last, when you are finished.

Rules:
- Do not modify anything in repo/ outside repo/_witness/. Do not modify Code
  Witness. If Code Witness is a limitation, work around it in your adapter or
  record it in BASELINE.md.
- No network access. Do not read outside this directory.
- Budget: 4 hours. If time is nearly up, freeze what you have and record the gaps.
- Do not ask the operator technical questions. The operator only helps with
  environment or permission failures.
```

Fill only the angle-bracket fields. Every operator response during this phase
goes in the intervention log.

### 9.2 Freeze

The freeze starts when `FREEZE-READY` exists or the investigator's budget runs out (S1).

1. Stop the investigator session and keep its transcript or command log.
2. Archive `investigator/repo/_witness/` as `sealed/baseline.tar`. Record the SHA-256 of the tar and of every file in it in `sealed/FREEZE.json`, together with the investigator's elapsed time, usage, turn count and restarts.
3. Post the `FREEZE.json` hash to PORT-110.
4. Audit the investigator's transcript for any path outside its workspace or any network attempt (S3, S4).
5. From now on the investigator workspace is read-only evidence.

### 9.3 Challenges

Start the challenger in a fresh session in `challenger/`, inside its isolation
boundary, with this prompt:

```text
repo/ is the source of <project name>. Its tests are removed; do not recover them.
Write 14 realistic maintenance regressions and 14 behavior-preserving changes to
repo/<target module path> and the repository modules it imports.

Regressions: the kind of mistake a competent maintainer could make during a
refactor or fix (boundary, default value, error handling, encoding, ordering,
state, type handling, missing case). Each one must change observable behavior
of the public API for some input. Avoid trivially detectable breakage such as
syntax errors, import failures or a function that always raises.

Behavior-preserving changes: refactors a maintainer might do (rename locals,
extract a helper, reorder independent statements, simplify an expression,
change comments) that do not change any return value, exception type or
message, or output for any input.

For each, write challenges/<R01..R14 or N01..N14>.patch (a unified diff against
repo/, applying with git apply) and challenges/<id>.json with "category",
"rationale" (one sentence) and, for regressions, "exposing_input": a short
Python snippet using the public API whose result differs before and after.
Work only in this directory, with no network. Budget: 1 hour.
```

Copy `challenger/challenges/` to `sealed/challenges/`, record hashes, audit the
transcript, and validate each challenge under section 3 with the adjudicator.

### 9.4 Scoring

All scoring runs from `scoring/` inside this sandbox profile. It denies network
access and allows writes only to `scoring/` and the temporary directory:

```bash
python3 - "$PWD" > scoring.sb <<'EOF'
import json, os, sys
print('(version 1)\n(allow default)\n(deny network*)\n(deny file-write*)')
print('(allow file-write* (literal "/dev/null") (subpath ' + json.dumps(sys.argv[1]) + ') (subpath ' + json.dumps(os.path.realpath(os.environ["TMPDIR"])) + '))')

```

Run every scoring command below as `/usr/bin/sandbox-exec -f scoring.sb <command>`.
`$S` is `.venv/bin/python tools/score.py`, and `$UP` is the preregistered
upstream pytest argv as a JSON list.

1. **Scoring tree.**
   - Clone the target at the pinned SHA into `scoring/tree`, outside the sandbox because cloning needs the network. This brings back the upstream tests.
   - Extract `sealed/baseline.tar` into `scoring/tree/_witness/` and add `_witness/` to `.git/info/exclude`.
   - Confirm every source fingerprint in `_witness/pack/manifest.json` matches the scoring tree. A mismatch stops scoring until it is explained (S5).
2. **Clean replay** (C2):
   `$S check --tree tree --pack tree/_witness/pack --upstream "$UP" --upstream-timeout <prereg> --runs 3`.
   Both suites must report `survived` on all 3 runs. If upstream fails, stop: the selection was wrong. If the baseline fails, C2 is not met and its mutation results are reported as unreliable.
3. **Coverage** (M2), measured separately per suite:
   ```bash
   .venv/bin/coverage run --branch --data-file=cov-baseline --include='<target scope globs>' tools/fixture_coverage.py tree/_witness/slice/legacy/batch.py tree/_witness/slice/fixtures/cases.json
   (cd tree && ../.venv/bin/coverage run --branch --data-file=../cov-upstream --include='<target scope globs>' -m pytest -q -p no:cacheprovider <upstream test path>)
   .venv/bin/coverage combine --keep --data-file=cov-union cov-baseline cov-upstream
   ```
   Report all three with `coverage json --data-file=<file>`.
4. **Mutants** (C3):
   `$S mutants --tree tree --scope <target scope files> --seed <prereg seed> --out mutants.json`, then
   `$S run --tree tree --pack tree/_witness/pack --upstream "$UP" --upstream-timeout <prereg> --mutants mutants.json --import-root <import root> --import-module <prereg modules> --out mutants.jsonl`.
   The scorer refuses to start a mutant on a dirty tree and restores the tree after every mutant, even on failure. Use `--start` and `--stop` to resume after an interruption, appending to the same `mutants.jsonl`.
5. **Challenges** (C4, C5). For each valid challenge in ID order:
   - `git -C tree apply sealed/challenges/<id>.patch`
   - `$S check --tree tree --pack tree/_witness/pack --upstream "$UP" --upstream-timeout <prereg>`
   - `git -C tree checkout -- .`
   - confirm `git -C tree status --porcelain` is empty
   A regression is detected when the witness suite reports `behavioral`. Upstream results are reported beside it.
6. **Adapter honesty** (C2):
   `$S knockout --tree tree --scope <target scope files> --pack tree/_witness/pack`.
   This replaces every target-scope function body with a raise. A fixture whose observation does not change never reached target-scope functions. The adjudicator also reads the adapter and records whether any of it reimplements target logic, with a rationale.

### 9.5 Adjudication

The adjudicator works from packets prepared by the coordinator in `adjudicator/`.
Each packet contains only what the judgment needs, and every verdict is recorded
in `sealed/ADJUDICATION.jsonl` with `id`, `question`, `verdict`, `rationale`,
`evidence` (commands run and their outputs) and `confidence`.

- **Equivalence**, for every valid mutant without a behavioral kill in either suite. The packet holds the mutant diff, the target-scope source and a runner for snippets on the pristine and mutated trees, presented in random order with neutral IDs and no suite outcomes. Verdicts: `equivalent`, `not-equivalent` (with an executed distinguishing input) or `indeterminate` (with what was tried and why it is unresolved).
- **Challenge validity** (section 3), and **false-alarm disputes** for controls the baseline flagged.
- **Adapter reimplementation** review (9.4 step 6).
- **Claims calibration.** Check up to 10 claims tagged `Verified` in `CLAIMS.md` (all of them if there are fewer; otherwise every k-th one in file order) against the pack and source, labelling each `supported`, `unsupported` or `false`. No criterion is attached.

Uncertainty is kept, not resolved by default. Indeterminate cases stay indeterminate in the report.

## Known limits of this design

- One target says little about the general case. The result is a data point and a list of failure modes, not a capability claim.
- Low star count reduces, but does not remove, the chance that models memorized the target or its tests.
- Mutation operators are syntactic. A high kill rate does not mean business-relevant behavior is covered, and equivalence verdicts are judgments, which is why their rationale and uncertainty are recorded.
- The challenger is an LLM. Its regressions approximate maintenance mistakes; they are not field defects.
- The knockout check proves fixtures reach target functions. It cannot prove an adapter does not also compute outputs itself, which is why the adjudicator reviews the adapter.
- The witness suite's case timeout (5 s) is fixed by the engine and differs from the upstream suite's timeout. Timeouts are reported but never counted as kills in the primary rate.

## Mechanics evidence (October 23, 2026)

This evidence is about the scoring machinery only, not about the experiment.

**Pilot on a scratch copy of the v0.3 voice-frame codec** (its 25 existing
fixtures were written with knowledge of the code, so this is not baseline evidence):
- A legacy-only baseline (INCONCLUSIVE, exit 0) replays clean and fails when the imported module is mutated in place. No modern copy is needed for mutation scoring.
- **Stale bytecode masks mutants.** A same-size `>` to `<` edit with an unchanged mtime passed replay while `__pycache__` held the old `.pyc`, and failed with 14 failing subtests after the cache was purged. Code Witness compiles the adapter from source but imports helper modules normally, as the README documents.
- **cosmic-ray does not run `test-command` through a shell.** A command written as `rm -rf <dir> && ...` passed every later word to `rm` and deleted the pilot venv's interpreter link and the generated test (scratch files only). The scorer therefore never uses `cosmic-ray exec`.
- The fixtures covered 100% of the codec's lines and branches, yet 7 of 73 mutants survived.

**Canary preflight** (`preflight_canary.sh`, Code Witness wheel built from `5cc6ea7`, CPython 3.13.16, macOS arm64):
- All 12 checks passed. 66 of 66 mutants were valid.
- Witness suite: 52 behavioral, 10 timeouts, 4 survived. Upstream suite: 25 behavioral, 41 survived.
- A missing upstream test path was classified as `error`, not a kill.
- The stale-bytecode edit was detected with the purge. The control without the purge was masked, which confirms the hazard the purge prevents.
- Knockout changed every fixture with the honest adapter and none with the dishonest one.
- The tree was clean and the sentinels outside it were intact afterward.
- A second run produced identical summaries and identical per-mutant diffs and outcome classes.
- A third run, inside the section 9.4 scoring sandbox profile, also passed all checks with the same outcome counts.

**Probe self-test** (`probe.py`):
- Unsandboxed, it fails: network, child-process network, the deny-read path and the deny-write path are all reported allowed.
- Under a profile that denies network, writes outside the workspace and reads of a secret directory, it passes, and reading the sentinel file inside that directory is denied.
- A deny path that does not exist makes it fail as untested.
- This shows the probe can tell isolation apart from its absence. It does not yet show that any agent runtime can be isolated; that is P1's job.
